* Rendering Pipeline

** STATUS -- v1 slice implemented (steps 1--6)
Written 2026-10-29 from a brainstorming session; § V1 SLICE records what is
built. The scope it serves
(interactive and layouts equally, native in

Where this file has a caller use =geoscribe= to project, warp, densify or

** THE PIPELINE
Two stages, so an interactive frame never repeats expensive work:

#+begin_src text
 prepare (slow, once per tile and level)       draw (fast, every frame)
 ---------------------------------------       ------------------------
 WKB / sink -> cull -> decimate -> clip    ->  [prepared tile]  -> camera transform -> backend
            -> tessellate -> style index        cached (LRU,        (a uniform on GPU)
                                                byte budget)
#+end_src

- *Layouts are the same pipeline with one view and no cache.* The device
  resolution (screen pixels, or print DPI) sets the decimation tolerance, so a
  300 DPI print keeps more vertices than the screen view of the same data.
- *Nazca never holds a feature collection.* Geometry streams through prepare;
  peak working memory is about one geometry plus the output buffers.

** INPUT
Two entry points, both borrowing rather than owning:

- *WKB bytes (=&[u8]=).* An external spec, so it is the geometry analogue of
  =architecture.org='s Rule 1. =geosetta= 0.27.0 writes it (=geometry/wkb.rs=), DuckDB
  emits it (=ST_AsWKB=), and GeoParquet and GeoPackage store it. Nazca reads it
  in place without building a geometry tree (=src/wkb.rs=, implemented
  2026-10-29).
  /Corrected 2026-10-29: this said nazca "can read a geometry's bbox before
  decoding the rest". WKB stores no bbox; finding one means reading every
  coordinate. Culling before decoding needs a bbox the source already stores
  (§ PREPARE)./
- *The =Sink= trait* (=src/sink.rs=: =point=, =points(&[[f64; 2]])=, and
  begin/end events for lines, polygons and rings) for every other source: =geo-types=, GeoArrow buffers, or
  =geosetta='s =GeometryRef::shape= walked by a caller's adapter (newer than
  0.27.0: true of its main at =5101342=, unreleased). It names the capability,
  not the provider.

Coordinates arrive in the map's CRS, or as geocentric XYZ for a globe
(§ GLOBE). Nazca applies camera transforms only.

The sink is *generic, not =dyn=*. A caller that projects through =geoscribe=
inside its sink gets that projection inlined into nazca's prepare loop (the
workspace builds release with =lto = true=), so the crate boundary costs one
fused pass, not two passes and an intermediate buffer.

** TILE GRIDS
A tile grid is an origin plus a resolution per zoom level, in map units.
XYZ Web Mercator is one instance; any projected CRS can define its own. This
lets interactive views use a per-view CRS, which MapLibre cannot.

- Prepared buffers are stored in *tile-local f32 coordinates*, which avoids
  the precision jitter of f32 world coordinates at street level. The camera
  transform is applied at draw time, so pan, zoom and rotate between
  levels of detail need no re-preparation.
- Raster tiles published in Web Mercator shown in another CRS need warping,
  which is =geoscribe='s (its § CHARTER: raster warping). See § RASTER for
  how that stays cheap.
- *Tile selection is behind a trait.* v1 ships the flat XYZ implementation;
  a globe selector (§ GLOBE) plugs in later. A tile's extent in device space
  comes from the grid's CRS, so non-trivial grids are implemented by the
  caller over =geoscribe=.

/Implemented 2026-10-29 (=src/grid.rs=):/ =TileGrid= holds an origin, a tile
size in pixels and one =Level= (span in map units, columns, rows) per zoom,
built by =web_mercator=, =quadtree= (any CRS whose levels halve) or =new=
(levels that do not, as some national grids have). It gives a tile's bounds,
the tiles covering a rectangle (an allocation-free iterator; an edge on a
tile boundary does not pull in the tile beyond, to within a billionth of a
tile), the level for a resolution (the coarsest that is not magnified), and a
=TileFrame= mapping map units to tile-local =f32= centred on the tile and
scaled to +-1. The grid is a concrete type; the selection trait is
separate, because it depends on the camera.

/Implemented 2026-10-30 (=src/select.rs=):/ =TileSelector::select(&Camera,
&mut Vec<TileId>)=, implemented on =TileGrid= as the flat selector: one
level, =level_for_resolution= at the camera's scale, the tiles overlapping
the viewport, nearest the view's centre first so an embedder fetching in
order fills the middle of the screen before its edges. A rotated viewport is
tested exactly (the separating-axis test, in map and in screen axes), not by
its map-aligned bounds, so a turned map does not fetch the corners of its
bounding box: a long thin view at 45 degrees needs under a third of the tiles
its bounds touch. The globe selector will implement the same trait.

** PREPARE
- *Cull* by bbox before decoding, using a bbox the source already stores:
  the GeoPackage envelope or R*Tree, GeoParquet's bbox covering column,
  FlatGeobuf's packed index. The caller passes it in or skips the feature
  itself. Without a stored bbox, culling happens after decoding.
- *Decimate*: drop consecutive points that land in the same device pixel.
  O(n), allocation-free, lossless at output resolution.
  /Changed when implemented, 2026-10-29: snap instead./ Dropping "the second
  point in a pixel" depends on which way a ring runs, so two polygons sharing
  a border would decimate it differently and open slivers between them. Each
  coordinate is instead snapped to a grid fixed in map units (a quarter pixel
  by default, as MVT's 4096 extent is), then repeats and exactly collinear
  middle points are dropped. On an integer grid both tests are exact, so
  neighbours agree point for point.
  /Changed 2026-10-30: point features are not snapped./ A tile standing in
  for one several levels down is magnified by the difference, and so is
  its snapping: a z5 tile shown at z10 put dots up to 4 CSS pixels off,
  and they jumped when the real tile arrived (found zooming
  fast). A lone point has no border to share and nothing to decimate, so it
  keeps its exact tile-local position.
- *Clip* to the tile plus a guard band, so off-tile coordinates never reach
  the rasterizer and line joins at tile edges stay clean.
- *Tessellate* polygons with earcut (hand-rolled, about 500 lines, or
  =earcutr=). Not =lyon=, which is heavier than needed.
  /Implemented 2026-10-29 as a port of mapbox/earcut v3/ (=src/earcut.rs=),
  under its ISC licence, whose notice the file and =../NOTICE= carry.
- *Lines are uploaded as centerlines* and expanded (width, joins, caps) in the
  vertex shader. That keeps prepare cheap and buffers small, and widths stay
  right at any zoom.
- *Style class index per vertex*, not baked colors (§ STYLING).

/Implemented 2026-10-29 (=src/prepare.rs=, =src/earcut.rs=)./ =MeshBuilder=
is a =Sink= for one tile (=for_tile=, or =new= with a =Detail=: tile size,
grid step, guard band). Rings are clipped by Sutherland--Hodgman, lines by
Liang--Barsky; a ring wholly inside skips clipping and one wholly outside is
dropped without it, and edges clipping creates along the clip boundary are
filled but not outlined. Verified on real data (=tests/prepare_counties.rs=):
cut into tiles with no guard band, all 3,222 US counties' fill area across
every tile matches their exact area -- within 3e-2 square degrees at worst,
four orders of magnitude inside the snapping bound -- and no vertex leaves its
tile. All 3,222 into the 2,560 tiles of a 512-pixel level 7 (degree grid)
takes 13 ms in release. That data is already a generalised 1:20M boundary
set, so decimation barely shows on it (79% of points kept at level 3); a
28-million-vertex roads layer is the honest benchmark for it.
Fine levels emit more vertices than they read (148% at level 9): clipping
adds points where borders cross tile edges, and each tile keeps its own.

Prepared tiles are flat =Vec<f32>= / =Vec<u32>= buffers. In the browser they
cross from a Web Worker to the main thread as zero-copy transferable
=ArrayBuffer=s, which is the only parallelism wasm has without COOP/COEP
headers. Natively, prepare runs on =std::thread=.

** TILE CACHE
- One LRU cache with one *byte budget* covers vector and raster. The embedder
  sets the budget.
- After a tile is uploaded to the GPU, its CPU copy is dropped. GPU memory
  holds the only copy (picking does not need CPU geometry; § HIT-TESTING).
- The camera reports which tiles it needs; the embedder fetches them and hands
  the bytes to prepare. While a level loads, the parent level is drawn scaled.

/Implemented 2026-10-30 (=src/cache.rs=):/ =TileCache<V>= is generic over
what it holds, so the embedder's value is an enum of the backend's mesh and
texture and one budget covers both. Tiles are keyed by =(source, TileId)=,
the source numbered by the embedder. A frame is =begin_frame=, then per source
=plan(source, grid, needed, &mut Plan)=, which writes the tiles to draw now
(finest level first, see the stencil claims in § BACKENDS) and those to fetch (needed, not cached, not already
pending; planning marks them pending), then =insert= or =fail= as fetches
finish.
- *Stand-ins*: a missing tile is covered by its nearest level of cached
  ancestors, or failing that by its cached children, so zooming out shows
  something too. Ancestors are found through the grid (=tiles_in= the
  tile's bounds at each coarser level), so grids whose levels do not nest
  work, with several partial ancestors.
- *Eviction* is least-recently-used by last plan or insert, but never takes a
  tile the current frame draws: if those alone exceed the budget the cache
  runs over rather than leave a hole on screen. Using a tile moves it to the
  back of the order, so eviction stops at the first current-frame tile.
- *Freeing is the caller's*: GPU objects are not freed by =Drop=, so
  =insert=, =remove=, =remove_source= and =set_budget= return what they let
  go of. =GpuMesh::bytes= and =GpuRaster::bytes= are the sizes to insert
  them at.
- *A fetch that finds nothing* is better inserted as an empty tile than
  failed: =fail= only clears the pending mark, and when to retry is the
  embedder's call.
- Tiles overlap (guard bands; a stand-in and its loaded neighbours), and
  the =gl= backend gives each pixel to one tile by stencil (§ BACKENDS), which
  is why =Plan::draw= lists the finest level first.

** RASTER -- through the same cache (user decision, 2026-10-29)
- Store the *raw band*, not colored RGBA: an =R8= texture for a categorical
  band like land cover, =R32F= for continuous data. The colormap
  is a lookup texture applied in the shader.
- That is 4x less memory than RGBA for u8 bands, and changing the colormap is
  instant, through the same mechanism as vector restyling.
- Categorical bands sample nearest-neighbour. Linear filtering of float
  textures needs a WebGL2 extension (=OES_texture_float_linear=), so
  continuous bands need a fallback where it is missing.
- Pre-rendered RGBA tiles (third-party XYZ PNG basemaps) are uploaded as is.
- *Mesh warp.* Warping is CRS math, so nazca cannot warp per pixel in a
  shader. Instead the caller has =geoscribe= project a coarse control grid
  (say 16x16 points per tile), and nazca draws the texture over that mesh;
  the GPU interpolates between control points. The CRS math stays in
  =geoscribe=, the per-pixel work stays on the GPU, and the error is a
  fraction of a pixel for most projections at tile scale. The same mechanism
  drapes rasters on the globe (§ GLOBE).

/Implemented 2026-10-30 (=src/raster.rs=, =src/style.rs=, =src/gl.rs=):/
=Raster::new(width, height, Band)= checks the band fills its size; =Band= is
=Categorical(&[u8])= (an =R8= texture, nearest), =Continuous { values,
nodata }= (=R32F=; NaN and =nodata= draw nothing), or =Rgba(&[u8])= as is.
A continuous band is filtered linearly where the GPU can (desktop GL always,
WebGL2 with =OES_texture_float_linear=, which glow enables when offered) and
the band has no =nodata= value to blend into its neighbours; otherwise
nearest. A NaN still erodes its linearly filtered neighbours by up to a
pixel. =RasterMesh::rect= draws an image in the map's CRS;
=RasterMesh::warped(frame, cols, rows, points)= stretches it over a
caller-projected control grid. =Colormap= is 256 RGBA8 entries, by value
(=categorical=, unlisted values transparent) or along a domain (=ramp=
through stops), uploaded as a 256 x 1 texture. Rasters are drawn with an
opacity, and claim their pixels by their own mesh. Verified in the spikes
with a lon/lat distance field warped onto Web Mercator through a 9 x 9 grid:
its rings come out as circles.

** STYLING -- decided 2026-10-29 (user decision)
- Plain Rust structs plus a per-feature callback that returns a style class.
  No nazca expression language: the embedder's own logic plays that role.
- Colors, widths and opacity live in a small *palette texture* indexed by
  style class. Restyling rewrites the palette only; no tile is re-prepared.
- Visibility and min/max zoom are per layer and checked at draw time.
- A MapLibre style-spec subset could come later as an optional adapter (an
  external spec, so Rule 1 friendly). Not in v1.

/Implemented 2026-10-30 (=src/style.rs=):/ =Style { fill, line, line_width,
point_size }=, colours as straight-alpha RGBA, and a =Palette= of 256 of them
(a class is a =u8=; unset classes draw nothing). The =gl= backend holds it as
a 256 x 3 =RGBA32F= texture (fill row, line row, width and point-size row)
read by =texelFetch=; =update_palette= restyles in one upload. Visibility
and min/max zoom are the embedder's for now: it chooses which layers to
draw.

/Zoom-dependent values, 2026-10-30:/ a =circle-radius= can follow
=["interpolate", ["linear"], ["zoom"], 3, 1, 10, 5]=. =style::interpolate(stops,
base, zoom)= evaluates MapLibre's linear and exponential curves, and
=TileGrid::fractional_level(units_per_px)= gives the zoom: on the 512-pixel
Web Mercator grid it is MapLibre's zoom exactly, and any grid has one. The
style stays plain values: the embedder re-evaluates its curves when the
zoom changes and rewrites the palette, one small upload, rather than nazca
growing an expression language.

** HIT-TESTING
- *ID-buffer picking*: render feature ids to an offscreen buffer and read back
  one pixel. Returns =(layer, feature_id)=; the embedder fetches attributes.
- No CPU-side geometry is kept for picking, which is what lets the cache drop
  CPU copies after upload.
- Reading pixels back stalls WebGL, so hover picking needs throttling. Click
  picking is effectively free.

/Implemented 2026-10-30 (=gl::Picker=):/ prepare stores a feature id per
vertex (=MeshBuilder::set_feature=, =Mesh::ids=). The picker redraws the
tiles into a *one-pixel* =RGBA32UI= framebuffer (with a stencil): a post
matrix maps the asked-for pixel onto the whole target, so its memory is 16
bytes whatever the viewport. Lines are expanded in the full viewport's
pixels before that mapping, so what picks is what draws; lines and points
narrower than a tolerance pick as if that wide. Fills pick even when
transparent. =Pick { layer, feature }=, with =layer= the embedder's number.
Rasters are not picked and do not hide features below them. Verified
natively and in Chrome's WebGL2 on the counties.

** CAMERA
Pan, zoom about a point, rotate, =fit_bounds=, and easing for animated
moves. Pure math with no event handling; the embedder calls it from its own
input events.

*Built on a 4x4 matrix from the start.* v1 uses it only as a flat 2D
orthographic view, but the type is ready for a perspective globe camera
without changing the backends or the shaders' interface.

/Implemented 2026-10-30 (=src/camera.rs=):/ =Camera= holds the centre in map
units, map units per pixel, a bearing and the viewport size. The bearing is
MapLibre's: radians clockwise from north to the map direction that points up,
so the map turns counter-clockwise on screen as it grows. =pan_px=,
=zoom_about= and =rotate_about= keep the map point under the pointer where it
is; =fit_bounds= frames a rectangle with padding at the current bearing;
=screen_to_map=, =map_to_screen=, =corners= and =visible_bounds= convert.
Screen positions are top-left origin, Y down, in whatever pixels the viewport
is sized in. =matrix(&TileFrame)= is the tile-local to clip-space =mat4=,
composed in =f64= so a tile's offset from the camera cancels before the cast:
a hundredth of a pixel at 0.1 m per pixel at Web Mercator's far east edge.
The =gl= backend's shader takes it as =uniform mat4=. Easing for animated
moves is not built yet.

** GLOBE -- after v1 (user decision, 2026-10-29)
MapLibre's globe projects Web Mercator to a sphere in the vertex shader. That
is CRS math, which nazca does not do (§ CHARTER in =../project.org=). The
charter-clean way:

- *The caller converts to geocentric XYZ* (EPSG:4978) with =geoscribe=. That
  is an ordinary CRS conversion.
- *Nazca renders 3D points with a perspective camera.* Camera math, no CRS.

What this gets for free from the rest of the design:
- *Precision*: tile-local coordinates (relative to each tile's centre) fix
  f32 jitter at Earth-radius scale exactly as they do in 2D.
- *Raster*: draped over a =geoscribe=-computed mesh, the § RASTER mesh warp.
- *Picking*: the ID buffer works unchanged in 3D.
- *The antimeridian*: geocentric coordinates have no seam at +-180.

What it costs:
- *Memory*: 3 floats per vertex instead of 2, about 50% more vertex memory,
  in globe mode only. Flat tiles keep 2D buffers.
- *Densification*: long edges must be densified before conversion or they cut
  through the sphere. Geographic work, so the caller does it with
  =geoscribe=, at a tolerance matched to the zoom level.
- *Tile selection is the hard part*: frustum and horizon culling, and level
  of detail chosen by distance rather than zoom, all needing each tile's 3D
  bounds before its data arrives. Nazca does the culling; the bounds come
  from the caller's tile-grid trait implementation over =geoscribe=.
- *Poles*: Web Mercator tiles stop near 85 degrees, so the globe needs polar
  caps filled.

** PERFORMANCE COSTS OF THE SEPARATION
The crate boundary itself is close to free (§ INPUT, generic sink).
What the charter does cost:
- *No projection in shaders.* Covered for the globe by § GLOBE and for
  warping by § RASTER's mesh warp.
- *Projection runs before decimation*, so every vertex is projected, including
  those decimation then drops. Mitigation: project upstream once (a tile
  server can =ST_Transform= and simplify in its database), or have the caller
  pre-simplify with =geoscribe= per zoom level. Either way it is paid once per
  tile at prepare, never per frame: the camera never re-projects.
- *Attribute lookups take a round trip* (from nazca not holding attributes,
  not from the charter). The embedder can cache them per tile if it matters.
- *One wasm module.* The consumer crate must compile =geoscribe= and nazca
  into a single wasm module; two modules would copy every coordinate buffer
  through JS.

** BACKENDS
| Backend | Feature | Used for |
|---------+---------+----------|
| GPU via =glow= | =gl= | interactive, browser (WebGL2) and native (OpenGL) |
| SVG writer | default | vector layouts |
| =tiny-skia= | =raster= | PNG export, server-side raster tiles |

Not a backend but also feature-gated: =mvt= (decoder, no dependency;
§ V1 FEATURES) and =text= (glyphs; § LABELS).

- =glow= over =wgpu=: a thin, pure-Rust GL binding that covers WebGL2 and
  native GL and adds tens of KB to a wasm build rather than megabytes. WebGPU
  can come later if a need appears.
- All backends replay the same draw-command buffer: flat opcodes plus
  =f32= data.
- *Native windowing is the embedder's.* An example under =examples/= using
  =winit= + =glutin= (dev-dependencies only) is the reference embedder.

/The =glow= backend, implemented 2026-10-30 (=src/gl.rs=):/
- *Fills*: the mesh's triangles, coloured from the palette texture.
- *Lines*: outline segments become instances of a quad expanded in the
  vertex shader around the segment, in pixels; the fragment shader keeps
  what lies within half the width, with a one-pixel antialiased edge. That
  gives round caps and joins with no neighbour information. Points are the
  same quad around a zero-length segment: a dot of =point_size= in the fill
  colour.
- *Each pixel belongs to one tile*, by stencil: a tile *claims* its square's
  unclaimed pixels (0 -> 2), draws only there (== 2), then *settles* them
  (-> 1). Tiles drawn finest first keep their area from coarser stand-ins;
  same-level guard bands never draw twice. The claimed square is grown by one
  pixel so the rounding of two neighbours' f32 matrices cannot open a seam;
  the guard band holds the same geometry there. =begin_layer= clears the
  stencil. The context needs a stencil buffer (WebGL leaves it out unless
  asked). Verified with translucent fills over 16 tiles: no tile edge shows.
- *Known limits*: a translucent line blends twice where segments' round ends
  overlap (darker dots at vertices), and a border two polygons share is
  outlined by both. Neither shows with opaque lines.
- /Changed 2026-10-30, with the SVG backend: no separate draw-command
  buffer./ The prepared =Mesh= is already flat =f32= / =u32= buffers, and it
  is what both backends replay. The GPU takes its triangles and outline
  segments; SVG takes its polygon rings (=Mesh::rings= and =Mesh::polygons=,
  added for it: a path is filled from rings, not triangles, whose seams
  would show) and the same outline segments. An opcode stream between them
  would be a second copy of the same data.

/The SVG backend, implemented 2026-10-30 (=src/svg.rs=):/ =SvgWriter= in the
default build. Fills come from the polygon rings, lines from the outline
segments chained back into polylines -- exactly the segments the GPU
strokes, so edges that clipping made are not stroked here either -- and a
=<circle>= per point.
/Changed 2026-10-30: one =<path>= per class for a whole layer./ Each layer's
fills, and its lines, are gathered over every =draw= into one path per
class, written when the layer ends; points follow. It was a path per
polygon, and a polygon split along tile edges then showed the background
through every split, because a viewer antialiases each path's edges on its
own. Rendered with =rsvg-convert=, an edge at x = 50.5 between two halves of
one 0.9-opaque black fill came out 77 against 25 elsewhere (255 white), and
63 against 0 for an opaque one; as one path, 25 throughout. Fills are
=nonzero=, with each exterior wound clockwise on screen and holes the other
way, so features in one path neither cancel nor blend twice. The cost: two
features of one class that overlap fill as their union, where the GPU
blends a translucent fill twice, and a layer's fills stack by class rather
than in feature order.
Styles are CSS classes written once, named per layer so two layers' palettes
cannot collide; coordinates are written to a hundredth of a pixel. A layout
prepares its one view with =MeshBuilder::for_view(&camera)=: a frame around
what the camera shows, at the camera's own resolution, so a 150 dpi page
keeps more vertices than the screen. Rasters are not written (an SVG image
needs encoded bytes, the =raster= backend's job). =examples/layout.rs= draws
an 8 x 6 inch page at 150 dpi: the MLT basemap tile under the WKB counties,
north up or turned, 37 KB of SVG; rendered with =rsvg-convert= the two
sources register exactly.

** LABELS -- after v1 (user decision, 2026-10-29)
Interactive labels must stay put across pan and zoom without flicker, which
is much harder than placing them once for a layout, so they are not in v1.
After v1: point labels with a stable priority order first; line
labels later. Glyphs come in
as font bytes from the embedder (no filesystem access, for wasm). The SVG
backend can emit =<text>= and let the viewer shape it.

** V1 FEATURES -- what v1 draws
- Layer types: fill, line, raster. No labels (§ LABELS).
- Sources: vector tiles as WKB, MVT or MLT, which the embedder may read out
  of PMTiles; XYZ raster tiles.
- Paint: fill and line colours with opacity, line width, raster opacity.
  Visibility and zoom ranges are the embedder's (§ STYLING).
- Interaction: picking, zoom and rotate about a point, fitting to bounds.

/Changed 2026-11-07 (user decision): this list no longer stands as a MapLibre
parity target, and nazca makes no claim of parity./

*MVT decoding lives in nazca, behind an =mvt= feature* (user decision,
2026-10-29). A few hundred lines: protobuf varints, the MVT geometry command
stream, feeding the sink directly with no intermediate geometry. Chosen over
=geosetta= so a consumer showing a basemap does not have to link a format
converter for it (geosetta 0.27.0 reads no MVT). Only geometry and feature ids are decoded; MVT properties
are skipped, matching nazca not holding attributes. Reading the PMTiles
container (a directory lookup over byte ranges) is the embedder's I/O.

/Implemented 2026-10-30 (=src/mvt.rs=)/, with *MLT beside it* (user,
2026-10-30), behind an =mlt= feature
(=src/mlt.rs=), also with no dependency.
- *MVT*: tiles, layers and features iterate over the borrowed bytes;
  =Feature::read(bounds, sink)= decodes the command stream straight into a
  =Sink= in map units. Polygon rings are grouped by winding, as MVT 2
  defines.
- *MLT v1*, the stable format, from the specification at
  =maplibre/maplibre-tile-spec= (commit =71f20ee=). Columnar, so a layer
  decodes whole: =Layer::decode()= reads the geometry and id columns into
  =Features= and parses every property column only far enough to skip it;
  =Features::read(i, bounds, sink)= feeds one feature. Every integer
  encoding a geometry or id stream can name is read: fixed-width, varint and
  the v1 SIMD-FastPFOR (256-value big-endian blocks, from the spec and the
  reference TypeScript decoder); delta, RLE and delta-RLE; vertices plain,
  componentwise-delta, dictionary and Morton. Polygons take their rings from
  the topology streams, not from winding, as the spec requires.
  Pre-tessellated triangles are skipped: their indices count vertices before
  nazca's snapping and clipping. Frames of other tags (the experimental v2)
  are skipped, as the spec requires of an unknown tag.
- *Verified* (=tests/vector_tiles.rs=): all 366 v1 conformance fixtures of
  the MLT specification decode to the geometry and ids their expected GeoJSON
  gives, and the four cross-language FastPFOR vectors decode
  (=tests/fixtures/fetch_mlt_fixtures.sh=; the spec's test data is licensed
  per source, so it is fetched locally, not checked in). One Massachusetts
  basemap tile in both encodings is checked in (=tests/fixtures/basemap/=,
  census-derived) and decodes to the same geometry from both; locally, eight
  tile pairs from z0 to z6 do (=make_basemap_fixtures.sh=).
- *Finding*: the tiler that built the fixture basemap (freestiler 0.3.0) writes
  MLT's 64-bit feature-id deltas without the zigzag encoding v1 requires
  ("each difference is zigzag-encoded ... whatever the stream's type"), so a
  conforming decoder reads them as wrapped negatives. nazca follows the spec
  and does not guess the writer. The geometry is unaffected.

*So v1 does not foreclose the globe* (§ GLOBE), it must also have:
- a camera built on a 4x4 matrix (§ CAMERA);
- a vertex format that allows 2D or 3D positions, chosen per tile;
- tile selection behind a trait (§ TILE GRIDS);
- mesh-warp raster drawing (§ RASTER).
These are cheap now and expensive to retrofit. The globe itself (camera
controls, sphere tile selection, polar caps, densification wiring in the embedder)
is the milestone after v1.
